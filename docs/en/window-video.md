# Window video and transparency

[简体中文](../zh-CN/window-video.md)

An application's root, owned dialogs and independent same-application windows each have their own capture worker, encoder, decoder and viewport. Ownership determines grouping and host authorization; it does not select a still-image codec. Global quality changes update all existing members, and new members inherit that quality.

The host advertises `window_video_alpha`; the client opts in with `alpha_video: true` when selecting an application session. With this capability, H.264 applies to every authorized member. Each H.264 packet may include an `alpha_png` sidecar: a grayscale PNG whose luminance is the alpha value. Color stays H.264. Fully opaque frames omit the mask; stable masks are cached even while color animates. Actual captured alpha is combined with native layered-window uniform opacity and color-key attributes. Rounded corners do not force full-color PNG video. Each sidecar accompanies its own frame, so resize, reconnect and encoder epochs require no separate mask-history synchronization. Mask payloads are limited to 6 MiB and decoded dimensions to 33,177,600 pixels.

Mask coordinates cover the source frame; the client scales the mask to the decoded video extent without color-space conversion. The Mac compositor preserves 8-bit partial alpha. The explicit image preset remains PNG/JPEG; clients without this capability retain the previous root-video/auxiliary-PNG behavior. Update both endpoints to use the optimized path. Native compositor effects beyond captured alpha and layered-window attributes still need broader device validation.

Each member accepts its own `video_viewport` dimensions and generation token. A global settings change advances every member's stream epoch, recreates capture when switching video/image mode, and discards queued packets from earlier epochs. H.264 reference frames within the current epoch remain ordered. The current host retains bounded per-window queues and hardware-to-software fallback; many simultaneous windows can exceed GPU encoder capacity and share network bandwidth.

On Mac, JSON parsing and Base64 decoding run on a connection-specific background queue with a 24 MiB input limit. Each surface has its own serial decoding/composition queue; a shared two-worker budget bounds concurrent decoding and resets on reconnect. With negotiated playback feedback, parsing and control delivery continue while any decoder is busy. Readers retain two delivery permits until parsing completes; queued video is separately bounded by 96 MiB (encoded data plus retained Base64 color/mask payloads), 64 jobs in total and four per surface. Disconnect releases readers and rejects old-connection completions; window generation and stream epoch prevent stale presentation. Older hosts retain decode-coupled read backpressure. PNG/JPEG decompression happens before UI presentation.

A native Mac title-bar drag stays local and keeps a per-window offset. Dragging the remote title bar forwards input; while the left button is held, group geometry is requested every 33 ms rather than every 200 ms. Known-window bounds refresh separately from catalog discovery. Unchanged-size video frames no longer repeat child layout. FPS/encoder/dimensions describe the last focused remote window; traffic includes all members of the application.

See [validation](validation.md) for the measured VM performance and limitations. GPU-native conversion/rendering, aggregate bandwidth adaptation, broader translucent-compositor cases and a physical GPU matrix remain future work.

## Anchored remote dragging

The host advertises `anchored_pointer`. A capable client sends `drag_begin` with a monotonically increasing gesture ID and a validated normalized start point, followed by `drag_move` / `drag_end` with cumulative source-pixel deltas from that start. Mac freezes the Quartz screen position and source-pixels-per-view-point ratio on mouse-down; Windows freezes the actual desktop cursor position. Neither endpoint rebases the gesture when window geometry or frames arrive. Queued moves within the same gesture can be replaced by the latest cumulative sample; start/end boundaries remain ordered.

The host validates window identity, membership and generation before input. Movement outside the target is accepted only while the target or a child owns native mouse capture, or that target is in the native move/size loop. Gesture mismatch, invalid deltas and lost capture fail closed; input errors, focus loss and disconnect release held input. Mouse-up outside the local viewer still ends the gesture. Old hosts retain the legacy normalized-pointer path. This keeps real remote dragging; it does not postpone movement until release or simulate a local proxy window.

The current connection uses TCP with TLS 1.3, with video and control messages sharing the ordered stream. The anchored-coordinate fix does not change transport or eliminate network/decode latency. A future QUIC evaluation could separate reliable controls from media delivery; unreliable video would also require sequence handling, reference-frame recovery, congestion control and bounded queues. See [QUIC transport](https://www.rfc-editor.org/rfc/rfc9000.html) and [QUIC datagrams](https://www.rfc-editor.org/rfc/rfc9221.html).

## Pipelined input and consumption feedback

The packaged bridge advertises `bridge_pipeline` locally. Its single TLS owner can have up to 32 requests outstanding and associates ordered replies with their original request, independently of unsolicited frames. `bridge_async` is local bridge metadata, accepted only for input and playback feedback and removed before network transmission. Mac allows up to 12 asynchronous input batches / 16 combined asynchronous requests. Inputs can pass pending read-only maintenance, but cannot cross a pending clipboard/selection barrier. An input acknowledgement never completes an unrelated control request. Connection loss discards queued input; it is never replayed. Acknowledgement means native injection completed, not that an application consumed the text; the documented rapid-switch stress issue remains open.

After authentication, host and streaming bridge use nonblocking sockets with bounded write turns, preserving partially written records. A busy video write does not prevent reading control input. The host produces frames independently of receive timeouts, so continuous input cannot starve capture. Framed records on one TCP stream still cannot overtake a partially transmitted video payload. During restricted sharing, queued frame authorization is checked before each write turn; if a partially sent record loses permission, the connection closes rather than finishing the revoked payload.

A host advertising `playback_feedback` accepts the same flag on selection after push streaming has started. Each window permits two sent-but-unconsumed frames. `video_feedback` names session, window, generation, stream epoch and sequence, with bounded `decode_ms` and `queue_ms`. Feedback is sent after decode/presentation handling, including empty decoder output and superseded-epoch completions. Old-epoch feedback frees only its actual credit. Duplicate, forged and invalid telemetry is rejected. A stopped consumer pauses only its window; the worker's bounded output eventually pauses encoding while capture retains recent raw data. Encoded H.264 reference frames are not arbitrarily dropped.

The current quality controller averages feedback over one-second observation windows and separates client pressure from delivery backlog. Parsing, decode-queue, UI/presentation and feedback-scheduling delay is included in the client's `queue_ms`; decode execution remains separate. Sustained client pressure reduces FPS only, retaining bitrate. Four sustained excess-delivery observations reduce FPS and traffic together while preserving at least 80% of the preset's bits-per-frame budget (and the protocol's 250 Kbps minimum). Delivery adaptation stops lowering FPS at 10 FPS or the user's lower ceiling; slow clients may go down to 5 FPS. One spike or alternating local/network observations do not combine into an automatic quality reduction. Idle gaps discard stale observations.

Changes have a four-second minimum interval. Recovery requires six healthy observations and at least eight seconds since the previous change. Bitrate recovers in steps of 20% of the ceiling; FPS increases only when its corresponding bit budget is available. Rate changes still restart the encoder with a new epoch. Source resolution is never lowered by this controller. It does not guarantee sharpness at every preset/content combination or solve TCP head-of-line blocking. If the link cannot sustain the clarity floor, consumption credits bound backlog at the expense of delivered FPS.

Hosts advertise `resolution_bitrate`; capable clients opt in on selection and live settings. The preset bitrate then describes a 16:9 canvas at its `max_width`. Larger actual encoded surfaces receive a proportional budget, capped at four times the preset and 20 Mbps per window, quantized in 250 Kbps steps to avoid encoder resets for tiny size changes. Smaller surfaces retain the base preset budget. Budget changes preserve existing adaptation reductions rather than resetting quality to full on each resize. Legacy requests without this flag retain fixed preset ceilings. The global preset still applies to all windows; pixel budgets and adaptation are per window, not an aggregate connection limit.

The Mac statistics show target FPS, target / pixel-budget Mbps and stable/client-busy/delivery-backlog/recovery state for the active surface. These are controller targets; measured FPS and app traffic remain separate. Receiver-local timestamps never go over the network. Bridge serialization and scheduling before client receipt remain part of observed delivery time, so delivery backlog is not proof of network congestion.

FFmpeg NVENC now uses P3 rather than P1, retaining ultra-low-latency mode, no B frames and no lookahead. The rate-control buffer allows up to three frames within 100 ms, or one frame when the frame interval exceeds 100 ms. This is an encoder budget, not an added frame queue. Hardware-specific quality, throughput and latency still require physical GPU validation.

This is an independently implemented design informed by RustDesk 1.5.3; see [source attribution](../../THIRD_PARTY.md). TCP/TLS and OPAQUE are retained. Binary local IPC, QUIC, aggregate bandwidth allocation, configurable credit windows for long-RTT links and physical GPU/loss-network tuning remain future work. Two in-flight frames intentionally bound latency but can limit throughput on high-RTT paths. The bridge still serializes Base64 JSON locally; background parsing and decoding keep this work off the UI thread but do not remove its serialization cost.

Negotiated [window management](window-management.md) supersedes the legacy root-scaled panel layout: independent windows stay separate, panels use their actual owner, and native border resize defaults to local scaling, with host geometry changes only in the explicit host-resize mode. Per-window video and feedback remain independent.
