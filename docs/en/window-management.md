# Window roles and remote window operations

[简体中文](../zh-CN/window-management.md)

A session groups authorized application windows across verified process instances. Window role and process membership are separate: one process can expose several independent windows, and another process can own a floating dialog. The host describes the role; all clients preserve it.

| Host role | Client presentation | Window operations |
|---|---|---|
| Independent | Separate native window; normal window switching/taskbar eligibility | Local close/minimize/maximize/restore; local scaling or explicit host resize |
| Floating | Owned native panel; excluded from normal taskbar/window cycling; follows its owner | Local close and scaling; optional authorized host resize; no separate minimize entry |
| Modal | Owned dialog; its disabled owner cannot receive remote input or host window actions | Operate the enabled dialog until Windows re-enables its owner |
| Transient | Borderless menu, dropdown or tooltip; no added title bar/taskbar item | Native remote input and host-controlled lifetime |

Windows/Linux clients map taskbar eligibility to their platform. macOS uses one Kokoda Dock application icon, individual normal windows for independent windows, and panels excluded from the Window menu for owned/transient surfaces. This is a shared behavior contract, not a requirement to share native rendering code. Windows/Linux GUI clients are still pending.

The negotiated `window_management` capability adds a per-member `presentation` object: physical-capture monitor DPI (`dpi`, legacy fallback 96), role, sanitized owner ID, enabled/minimized/maximized state and close/minimize/maximize/resize capabilities. Root selection is a session anchor, not a presentation role. An independent member is never attached as a child of that anchor. Floating/modal/transient members attach to their actual authorized owner when present. If the initial root closes in unrestricted application mode, another surviving independent member becomes the anchor; restricted mode still fails closed on root loss. Remote geometry and native lifecycle changes do not echo as user actions.

Client title-bar close, minimize, maximize and restore always affect the local viewer only, including in host-resize mode. Decorated viewers keep an enabled local close button even when the host cannot close, the parent is blocked by a modal dialog, or sharing is read-only. Buttons drawn inside the streamed application still operate the host through normal remote input. Closing a viewer hides its owned subtree, releases held input and preserves independent siblings. Snapshots and late frames must not reopen it. Reopen Locally Closed Windows in the Window menu, or open the application again from the catalog, restores its local viewers. Closing a local modal viewer does not dismiss the host dialog or unblock its owner; restore it to operate the dialog.

Each decorated viewer, including floating panels, exposes a native title-bar selector: **Scale view** (default) or **Resize host**. The Window menu provides the same choices and 50–200% display scale. Changing a selector targets its own window and returns keyboard/IME focus to its content.

In local scale mode, dragging either border or a corner adjusts both dimensions to preserve the displayed image's aspect ratio, with no viewer-added letterboxing or stretching. Local maximize fits the largest proportional content rectangle in the available screen. When the source aspect changes, the viewer follows the newly displayed frame, retaining width where it fits on screen. Sub-point native frame rounding is covered by proportional rendering to avoid thin seams; blank areas already inside the source window remain part of its image.

**Resize host** unlocks width and height independently and requires an enabled, resizable target with full control. A border gesture changes the source window's physical dimensions, not monitor resolution or system scaling. Returning to local scale fits the current image immediately. If permission or target capability becomes unavailable, the selector disables host sizing, explains the reason in its tooltip and falls back to local scaling. Native close/minimize/maximize/restore remain local in both modes. Source video may briefly retain its old aspect while a host size change is pending.

At 100%, local points = captured physical pixels × 96 / host monitor DPI. For example, a 1200-pixel window on a 250% Windows display occupies 480 Mac points. A 2× Retina screen then requests 960 video pixels for those 480 points; it does not double the host resize request. The host reports monitor scale even for DPI-unaware apps, whose captured pixels are already enlarged by Windows. New popups initially inherit the owner's logical display scale; subsequent client geometry is independent. This is UI size normalization, not a guarantee of identical physical size in centimetres or additional source detail.

Local geometry, resize mode and dismissal survive automatic reconnection for matching members. Removed/replaced members and explicit end-viewing/disconnect clear the preferences. Hidden viewers retain their decoder and at most the negotiated in-flight frame credits (currently two), withholding consumption feedback until restored, so late video cannot reopen them or build an unbounded queue. This pauses delivery, not destruction of the host capture worker. Legacy hosts without feedback continue decoding hidden video. End Viewing This Application releases the whole viewing session; neither it nor disconnect closes remote applications. The host revalidates generation, scope, native identity and enabled state for every remote action, including resize.

`window_action` carries session, window ID, generation token and `action` (`close`, `minimize`, `maximize`, `restore`, `activate`, `resize`). Resize includes bounded physical visible-frame width/height, optional left/top coordinates for anchored edges, and a client revision. Windows translates visible DWM bounds to the native outer frame, respects native minimum/maximum tracking sizes and lets the app constrain the result. Close is posted as WM_CLOSE; window actions never synthesize mouse movement. Potentially blocking native size constraint calls use a timeout. Async native operations are requests, not proof the target accepted them; snapshots remain authoritative.

In host-resize mode, native live resize responds locally immediately. Freeze source-pixels-per-Mac-point at gesture start (excluding the Mac title bar); Retina backing scale affects video resolution only. AppKit emits live-resize notifications during native zoom too; platform wrappers mark those actions as local before notifications arrive. Coalesce size updates at roughly 100 ms, preserve a final revision on release, and do not allow old geometry snapshots or group layout to overwrite a live/pending resize. After the final response, wait briefly for observed geometry to settle and reconcile to actual host bounds. A host geometry change resizes the local view only in this mode; unchanged snapshots must not undo local maximize/restore. Per-window viewport updates remain independently debounced. No resize gestures survive disconnect.

Discovery is host-local. The existing bounded periodic catalog refresh discovers new windows; native event hooks can later reduce polling latency. Follow verified owner chains and same-executable descendant process instances (canonical executable path plus PID and creation time), with a bounded process-tree refresh. A same-name executable, same vendor, common ancestor, or temporal proximity to a click is insufficient. A previously observed descendant remains eligible only while its exact process instance exists. Unrelated instances and external browsers are not automatically enrolled. Ownerless helpers using a different executable or broker-launched existing processes require separate selection today; explicit helper-family configuration is future work. Membership never grants sharing permission: filter the host catalog before grouping and recheck capture/input. No private titles or executable paths are sent as discovery hints.

The initial Windows classifier uses native owner, APPWINDOW/TOOLWINDOW styles, known menu/tooltip/dropdown classes and enabled-owner state. It does not claim perfect classification of every custom UI toolkit. Unknown unowned top-level windows remain independent; ordinary owned windows remain floating, and custom cases can be refined through synthetic regression fixtures.
