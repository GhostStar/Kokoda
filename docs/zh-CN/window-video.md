# 窗口视频与透明度

[English](../en/window-video.md)

应用主窗口、拥有关系中的对话框、同应用独立窗口分别拥有采集线程、编码器、解码器和视口。拥有关系决定分组及主机授权，不决定使用图片编码。全局画质切换更新全部已有成员，新出现的窗口继承当前画质。

主机声明 `window_video_alpha` 能力，客户端选择应用会话时通过 `alpha_video: true` 启用。启用后，H.264 覆盖所有获准窗口。每个 H.264 数据包可携带 `alpha_png`：亮度值代表透明度的灰度 PNG 遮罩，彩色画面仍用 H.264。不透明帧不带遮罩；画面运动但遮罩不变时复用缓存。实际采集 alpha 会结合 Windows 分层窗口的整窗透明度及透明色键属性。圆角不会导致整个视频退回彩色 PNG。遮罩与对应帧一起传递，缩放、重连和编码器代次切换无需维护额外遮罩历史。单个遮罩限制 6 MiB，解码尺寸限制 33,177,600 像素。

遮罩覆盖源画面坐标，客户端不对遮罩作色彩空间转换，并缩放到视频解码尺寸；Mac 合成保留 8 位半透明。显式图片档位仍使用 PNG/JPEG，未协商能力的旧客户端保留原有主窗口视频／附属窗口 PNG 行为。需同时更新两端才能启用优化。实际像素及分层窗口属性以外的原生合成器特效仍需更多设备验证。

每个窗口单独接收带代次令牌的 `video_viewport`。全局画质切换提升所有成员的流代次；视频／图片模式切换时重建采集，丢弃旧代次排队数据。同一代次的 H.264 参考帧保持顺序。主机保留每窗口有界队列及硬件失败后的软件回退；大量同时播放的窗口可能超过 GPU 编码能力，且共用网络带宽。

Mac 的 JSON 解析与 Base64 解码使用每条连接独立的后台队列，输入上限为 24 MiB。每个窗口分别使用串行解码／合成队列，共享两个并发解码名额；重连时重置并发控制。协商消费反馈后，即使某个解码器繁忙，解析及控制响应仍继续处理。读取方保留两个投递许可，解析完成即释放；视频积压另设 96 MiB 上限（编码数据及保留的 Base64 彩色／遮罩载荷）、全局 64 个任务及每窗口 4 个任务。断线释放读取方并拒绝旧连接结果，窗口代次及视频代次防止旧画面覆盖。旧主机保留与解码关联的读取背压。PNG/JPEG 在界面呈现前完成解压。

拖动 Mac 原生标题栏仅改变本地位置，保持窗口独立偏移。拖动画面内的远端标题栏则转发输入；按住鼠标左键时，位置同步请求由每 200 毫秒提高到每 33 毫秒，已有窗口的坐标刷新与目录发现分开。尺寸不变的视频帧不再反复触发布局。帧率、编码器和尺寸显示最后聚焦的远端窗口，流量统计包含该应用全部成员。

虚拟机测量与边界见[验证记录](validation.md)。GPU 原生格式转换／呈现、总带宽自适应、更多透明合成器情况及物理 GPU 矩阵仍待完善。

## 固定起点的远端拖动

主机声明 `anchored_pointer`。支持的客户端通过 `drag_begin` 发送递增手势编号及经过验证的归一化起点，后续 `drag_move` / `drag_end` 携带相对起点的累计源画面像素位移。Mac 在按下时固定 Quartz 屏幕坐标及源像素／视图点倍率，Windows 固定当时实际桌面鼠标坐标。窗口位置或新帧到达时，两端都不重设拖动基准。同一手势排队的移动可以由最新累计值替换，开始与结束边界仍保持顺序。

主机在输入前验证窗口身份、成员关系及代次。只有目标或其子控件实际持有鼠标捕获，或该目标处于原生移动／缩放循环时，才允许越出目标窗口移动。手势不匹配、无效位移及丢失捕获会被拒绝；输入错误、焦点丢失及断线会释放已按下的输入。鼠标在本地画面之外松开也会结束手势。旧主机保留原有归一化指针路径。此方案仍实时拖动远端窗口，不延迟到松开才提交，也不模拟本地替身窗口。

当前连接采用 TCP + TLS 1.3，视频与控制消息共用有序流。固定坐标修复不改变传输协议，也不消除网络／解码延迟。后续可评估 QUIC，将可靠控制与媒体传递分开；不可靠视频还需处理序号、参考帧恢复、拥塞控制及有界队列。参见 [QUIC 传输](https://www.rfc-editor.org/rfc/rfc9000.html)及 [QUIC 数据报](https://www.rfc-editor.org/rfc/rfc9221.html)。

## 连续输入与消费反馈

随包 bridge 在本地声明 `bridge_pipeline`，单个 TLS 收发方允许最多 32 个在途请求，按顺序将响应关联回原请求，推送视频不占用请求响应。`bridge_async` 是仅供本地 bridge 使用的标记，只允许输入及播放反馈使用，发往网络前删除。Mac 最多保留 12 批异步输入／16 个合计异步请求。输入可以越过等待响应的只读维护请求，但不越过尚未完成的剪贴板／窗口选择操作；输入确认不会误完成其他控制请求。断线丢弃排队输入，不重放。确认只代表完成原生注入，不代表应用已经消费文字；已记录的快速跨应用切换压力问题仍未解决。

认证完成后，主机和流式 bridge 使用非阻塞套接字及有界写入轮次，保留部分发送的记录。视频写入繁忙时仍可读取控制输入。主机发帧不再依赖读取超时，连续输入不会饿死画面发送。同一 TCP 流中的消息仍无法越过已经开始发送的视频载荷。受限共享在每轮写入前复查排队画面的授权；部分发送的记录若失去权限，会关闭连接而不继续发送已撤销载荷。

主机声明 `playback_feedback`，客户端开启推流后在选择窗口时通过同名标记启用。每个窗口最多两帧已发送但未消费的画面。`video_feedback` 包含会话、窗口、窗口代次、视频代次、序号，以及有界的 `decode_ms`、`queue_ms`。解码／呈现处理完成后反馈；解码暂未产出图片或旧视频代次结果被忽略时也归还对应额度。旧代次反馈只能释放实际对应的在途帧，重复、伪造及无效指标被拒绝。某个窗口停止消费只暂停自身；编码输出队列满后停止继续编码，采集侧保留较新的原始画面，不随意丢弃已编码的 H.264 参考帧。

当前控制器按一秒观察窗口取反馈均值，区分客户端压力与传输积压。解析、解码排队、UI／呈现和反馈等待时间均计入客户端 `queue_ms`，解码执行时间单独统计。客户端持续繁忙时只降低 FPS，保留码率。连续四次观察到额外交付积压时，同时减少帧率与流量，至少保留档位每帧比特预算的 80%，并遵守协议 250 Kbps 下限。传输调整最低降至 10 FPS 或用户设定的更低上限；客户端解码慢时可降至 5 FPS。单次尖峰、交替出现的本地与传输压力不会累加成降档，空闲间隔会丢弃过期观察值。

调整间隔至少四秒；恢复要求六次健康观察，且距离上次调整至少八秒。码率按上限的 20% 逐步恢复，只有对应比特预算足够时才提升 FPS。速率改变仍通过新视频代次重启编码器，此控制器不降低源分辨率。该策略不保证所有档位／内容都清晰，也不消除 TCP 队头阻塞；链路无法承载清晰度下限时，由消费额度限制积压，实收 FPS 会下降。

主机声明 `resolution_bitrate`，新客户端在选择窗口及切换全局档位时显式启用。档位码率代表以 `max_width` 为宽度的 16:9 参考画布；实际编码面积更大时按比例增加预算，最多为档位四倍及每窗口 20 Mbps，以 250 Kbps 为步长，避免微小尺寸变化反复重建编码器。较小画面保留基础预算。尺寸变化保留已有降档比例，不会每次缩放都回到最高速率。未启用该能力的旧请求仍使用固定档位上限。全局档位仍作用于全部窗口，但像素预算与自适应分别计算，不是整条连接的总带宽上限。

Mac 统计面板显示当前窗口的目标 FPS、目标／像素预算 Mbps，以及稳定／客户端忙碌／传输积压／恢复状态。这些是控制器目标，实收 FPS 与应用总流量仍单独显示。本地接收时间戳不发往网络。客户端收到数据之前的 bridge 序列化和调度仍计入观察到的交付耗时，因此“传输积压”并不证明网络发生拥堵。

FFmpeg NVENC 从 P1 调整为 P3，保留超低延迟、无 B 帧、无前瞻。码率控制缓冲允许最多三帧且不超过 100 ms；帧间隔超过 100 ms 时保留一帧预算。这是编码预算，不是新增画面排队。硬件编码画质、吞吐和延迟仍需物理显卡实测。

设计参考 RustDesk 1.5.3，按 Kokoda 自身协议独立实现，见[来源声明](../../THIRD_PARTY.md)。保留 TCP/TLS 与 OPAQUE。二进制本地 IPC、QUIC、总带宽分配、适应长 RTT 的可配置在途帧数及物理显卡／丢包网络调优仍待实现。两帧上限主动限制积压，但在高 RTT 链路可能限制吞吐。本地 bridge 仍使用 Base64 JSON；后台解析与解码避免占用 UI 线程，但没有消除序列化成本。

协商[窗口管理](window-management.md)后，独立窗口分别展示，面板跟随实际 owner，原生边框默认缩放本地画面，仅显式主机尺寸模式调整主机窗口大小，不再沿用所有弹窗按根窗口缩放的旧布局。各窗口的视频及反馈仍独立运行。

## 指针命中与带位置滚轮 — 2026-11-22

执行输入时显式进入 per-monitor-v2 DPI 上下文，返回时恢复调用者上下文。命中检查、鼠标定位与读回使用物理坐标 API，与 DWM 采集边界保持一致。目标激活后重新验证身份并读取边界，不再使用激活前的屏幕位置；如果激活改变了尺寸，仍等待新帧。微软说明：[物理坐标命中](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-windowfromphysicalpoint)、[DWM 边界与 DPI 虚拟化矩形的区别](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowrect)。

`positioned_wheel` 能力声明新增 `wheel_at` 事件，包含图像内归一化 `x/y`、源窗口物理 `width/height` 和有界 `delta`。Mac、Qt 使用一条自带位置的滚轮事件；旧主机保留先移动再滚动的兼容路径。Qt 指针同样改用归一化坐标及源尺寸，不依赖本地缩放。禁用输入、画面边缘外或正在进行锚定拖动时，不发送滚轮事件。

真正被遮挡仍拒绝输入，不因同进程、owner 或置顶属性绕过成员及命中校验。失败诊断只包含原因分类、目标 DPI、前台及 layered 标记，不暴露私人标题、路径、类名及遮挡窗口身份。用于区分屏幕外、模态禁用、同进程或其他进程表面，不能把所有命中失败都解释成肉眼可见遮挡。

交互式合成回归：配置 Windows SDK/FFmpeg 开发环境后，在交互桌面运行 `cargo run -p kokoda-platform-windows --example input_probe --target x86_64-pc-windows-msvc`。仅创建测试窗口，验证激活时位移、DPI-unaware 调用方带位置滚轮、真实置顶遮挡，最后关闭测试窗口。这不等于特定版本微信的验收。
